# フィード閲覧機能 テスト仕様書

## 1. テストの目的

タスク完了によって付与されたフィードの利用権利について、ユーザーが実際にフィードを開いた時点から3分間利用できることを確認する。

初回説明、再読み込み、画面の出入り、再ログイン、重複操作があっても、アカウントごとの閲覧期限が一貫して管理されることを確認する。

特に、説明を読んでいる時間による利用時間の減少、クライアント操作による期限のリセット・延長、期限後の閲覧やリアクションの継続を重大なリスクとして扱う。

本書は、事前に自分で整理した[テスト観点](../test-viewpoints/feed-access.md)を基に、ユーザーへの影響が大きいケースをまとめた結合テスト仕様書である。SmartHR Tech Blog『[結合テスト工程へのAI導入の現在地](https://tech.smarthr.jp/entry/2026/09/08/093129)』を参考に、仕様書の作成にはAIを活用した。その後、ユーザーへの影響を踏まえて、期待結果や優先度を自分で確認・修正した。

## 2. テスト対象

- タスク完了時のフィード閲覧権付与
- 初回説明モーダルの表示と「OK」による閲覧開始
- 画面のカウントダウンとサーバーの閲覧期限の同期
- 再読み込み、画面再訪、再ログイン、別ブラウザでの期限引き継ぎ
- 期限切れ時のフィード取得、表示、いいね、コメントの制限
- 初回説明確認状態の現行のブラウザ管理、および変更予定のアカウント管理
- 通信失敗・遅延・重複操作時の状態整合性

投稿内容、ページネーション、プロフィール表示など、閲覧時間の制御に直接関係しないフィード機能は対象外とする。

## 3. 前提とする仕様

### 現在の仕様・実装

- タスク完了時に、サーバーの `feed_access_expires_at` は完了時点から3分後に設定される。
- 初回説明未確認かどうかは、ブラウザの `localStorage` の `onestep-feed-intro-seen` で判断する。アカウントには紐づかない。
- 初回説明未確認でタスクを完了すると、フロントエンドは `defer_feed_access: true` を送り、サーバーの `feed_access_pending` を開始待ちにする。
- 初回説明の「OK」で `POST /api/feed/access` を実行する。開始待ちの場合だけ、開始待ちを解除して期限をその時点から3分後に更新する。開始待ちでなければ期限を延長しない。
- 説明確認済みの場合は、タスク完了時点から3分間が始まる。
- フィード取得時、サーバーは期限を基準に `remaining_seconds` と `feed_access_expires_at` を返す。期限切れの場合は `access_allowed: false` と空の投稿一覧を返す。
- 画面のタイマーはサーバー応答の残り時間・期限から開始する。初回説明モーダルの表示中は画面上のカウントダウン処理を停止する。
- 期限切れ時、画面は「3分経過しました」モーダルを表示し、フィード一覧を操作対象から外す。
- 開始待ち中でも、未来の `feed_access_expires_at` があれば `GET /api/feed` は投稿を返す可能性がある。
- いいね・コメントAPIには、閲覧期限の検査がない。

上記は現行挙動の整理であり、開始待ち中の投稿取得と期限切れ後のリアクションAPI利用は、変更予定の仕様とは異なる。

### 変更予定の仕様（未実装）

- タスク完了時は閲覧期限を開始せず、フィードを利用できる権利だけをアカウントに付与する。
- 初回説明の確認状態を `localStorage` ではなく、認証済みアカウントごとにサーバーで永続化する。
- 同じブラウザでアカウントを切り替えても、各アカウントの確認状態に応じて表示する。
- 同じアカウントでは、ブラウザ・端末・再ログインをまたいで同じ確認状態を使う。
- 初回ユーザーは説明モーダルの「OK」を押した時点、説明確認済みユーザーは「みんなを見る」を押してフィードを開いた時点から3分間を開始する。
- 初回説明の確認状態の保存と閲覧開始の一方だけが成功しないよう、整合性を保って処理する。
- 閲覧開始前は `GET /api/feed` から投稿を返さない。
- 一度開始した期限は、再読み込み、画面再訪、再ログイン、開始APIの再実行や重複操作では延長しない。
- 期限切れ後は、フィード取得だけでなく、いいね・コメントAPIもサーバー側で拒否する。
- 3分経過後は、新しいタスクを完了して新しい利用権利を得るまで再開できない。

初回説明の「OK」後に閲覧を開始する処理と、開始APIを逐次再実行しても期限を延長しない処理は一部実装済みである。それ以外は変更予定・未実装であり、各テストケースの対応状況に記載する。

## 4. テストデータ

| データ | 状態 | 用途 |
| --- | --- | --- |
| アカウントA | 初回説明未確認、完了可能なタスクあり | 初回表示、開始タイミング、別ブラウザ確認 |
| アカウントB | 初回説明確認済み、完了可能なタスクあり | 再表示抑止、同一ブラウザでの切替確認 |
| アカウントC | 閲覧期限切れ、完了可能な新しいタスクあり | 期限後制御、再解放確認 |
| 投稿P | 他ユーザーの投稿、いいね・コメント可能 | 閲覧・操作の期限確認 |
| ブラウザ1・2 | ストレージを共有しないコンテキスト | アカウント／端末境界の確認 |

時間依存ケースでは実時間を3分待たず、Railsの時刻固定またはフロントエンドの偽時計を使う。E2Eでクライアント時刻を進める場合も、サーバー期限の検証はAPI・結合テストで別途行う。

APIの閲覧期限を確認する自動テストでは、通信時間を考慮して約2秒の誤差を許容する。

## 6. 自動テストの種類と役割

| 種類 | 主な確認範囲 |
| --- | --- |
| フロントエンドAPI単体（Vitest） | 応答の変換、期限・残秒の受け渡し、401・通信失敗・異常応答 |
| コンポーネント／フック単体（Vitest＋偽時計） | モーダル中の停止、OK処理中の無効化、残秒表示、期限到達、失敗後の再試行 |
| Rails API・結合（RSpec） | タスク完了による期限付与、閲覧開始処理の重複防止、重複・並行リクエストの非延長、期限後の全API拒否、アカウント別確認状態の永続化 |
| UI結合（APIモックPlaywright） | モーダル、カウントダウン、エラー表示、期限切れ画面などの画面状態遷移 |
| 実バックエンドE2E（Playwright） | Cookie・アカウント切替・再ログイン・再読み込み・複数ブラウザと、サーバー期限をまたぐ重要導線 |

実時間を待つテストは避ける。正確な期限計算と排他制御はAPI・単体テストへ寄せ、E2Eはレイヤー間の接続が重要な少数のP0/P1シナリオに絞る。

## 7. 現在確認できている項目と不足項目

### 現在の実装・既存テストで確認できていること

- タスク完了でサーバー期限が約3分後に設定される。
- 開始待ち中の `POST /api/feed/access` で期限を押下時点から3分後にし、開始待ちを解除する。
- 開始待ちでない状態で同APIを逐次再実行しても期限を延長しない。
- `GET /api/feed` がサーバー基準の残秒・期限を返し、期限切れ時は投稿を返さない。
- フロントエンドがサーバーの残秒・期限をタイマーへ渡し、説明モーダル中はタイマーを動作させない構造になっている。
- UIの偽時計で3分後に終了モーダルを表示し、ホームへ戻れる。
- 主要フローで、タスク完了後にフィードを表示できる。

### 不足していること

- 説明を一定時間読んだ後でも、押下後に完全な3分が確保されることの実バックエンドE2E。
- 「OK」の多重押下防止、および開始APIの並行実行時にも期限が延長されないこと。現在のコントローラーは確認と更新を排他的に行っていない。
- 再読み込み、画面再訪、再ログイン後にサーバー期限を引き継ぐE2E。
- 期限後のいいね・コメントAPI拒否。現行実装では認証のみで、閲覧期限による拒否がない。
- バックグラウンド復帰や端末時計差がある場合のサーバー期限への補正。
- アカウント単位の初回説明確認。サーバー管理への変更後に、同一ブラウザでのアカウント切替と別ブラウザでの同一アカウントを追加確認する必要がある。
- 説明確認保存または開始APIが失敗した場合の、再試行可能で矛盾しない状態遷移。
- タスク完了では利用権利だけを付与し、初回かどうかにかかわらず実際にフィードを開いた時点で期限を開始する処理。

## 8. 仕様判断の結果

1. 閲覧開始前は、`GET /api/feed`から投稿を返さない。変更予定・未実装。
2. 期限切れ後は、いいね・コメントAPIもサーバー側で拒否する。変更予定・未実装。
3. 初回説明の確認状態は、アカウントごとにサーバーへ保存する。変更予定・未実装。
4. 初回説明の確認状態の保存と閲覧開始の一方だけが成功しないよう、整合性を保って処理する。変更予定・未実装。
5. 初回かどうかにかかわらず、閲覧時間はユーザーが実際にフィードを開いた時点から開始する。変更予定・未実装。
6. 一度確定した閲覧期限は、重複操作、再読み込み、再訪、再ログイン、開始APIの再実行では延長しない。重複操作への対応は変更予定・未実装。
