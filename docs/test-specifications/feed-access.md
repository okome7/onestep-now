# フィード閲覧機能 テスト仕様書

## 1. テストの目的

タスク完了によって付与されたフィードの利用権利について、ユーザーが実際にフィードを開いた時点から3分間利用できることを確認する。

初回説明、投稿の先読み、再読み込み、画面の出入り、再ログイン、重複操作があっても、アカウントごとの閲覧権利と期限が一貫して管理されることを確認する。

特に、フィードを開く前や説明を読んでいる間の利用時間減少、クライアント操作による期限のリセット・延長、期限後の閲覧やリアクションの継続を重大なリスクとして扱う。

本書は、事前に人間が整理した[テスト観点](../test-viewpoints/feed-access.md)を基に、ユーザーへの影響が大きいケースをまとめた結合テスト仕様書である。SmartHR Tech Blog『[結合テスト工程へのAI導入の現在地](https://tech.smarthr.jp/entry/2026/09/08/093129)』を参考に、テスト観点は人間が整理し、仕様書の作成にはAIを活用した。その後、ユーザーへの影響を踏まえて、期待結果や優先度を人間が確認・修正した。

## 2. テスト対象

- タスク完了による1回分の未使用閲覧権利の付与
- タスク完了後の投稿先読みと、先読み失敗時の扱い
- 初回説明モーダルの表示と「OK」による閲覧開始
- 説明確認済みユーザーがフィードを開く際の閲覧開始
- 画面のカウントダウンとサーバーの閲覧期限の同期
- 再読み込み、画面再訪、再ログイン、別ブラウザでの状態引き継ぎ
- 開始前、期限切れ時のフィード取得、表示、いいね、コメントの制限
- 通信失敗、遅延、重複・並行操作時の状態整合性

投稿内容そのものやプロフィール表示など、閲覧権利と閲覧時間の制御に直接関係しない機能は対象外とする。ページネーションは、開始前の追加取得禁止と、開始後の有効化のみを対象とする。

## 3. 前提とする現在の仕様・実装

### 3.1 閲覧権利の付与

- タスク完了時は、初回説明の確認状態にかかわらず、1回分の未使用閲覧権利を付与する。
- タスク完了時の状態は `feed_access_pending: true`、`feed_access_expires_at: nil` とし、まだ3分間を開始しない。
- 未使用閲覧権利は回数として蓄積しない。新しいタスク完了時は、既存の状態を新しい1回分の未使用閲覧権利へ置き換える。
- 3分経過後は、新しいタスクを完了するまで閲覧を再開できない。

### 3.2 投稿の先読み

- タスク完了APIの成功後、フロントエンドは `GET /api/feed` で最初のページを1回だけ取得し、メモリ上に保持する。
- 先読みした投稿はタスク完了画面には表示しない。
- 先読みでは閲覧時間、タイマー、Action Cable購読、投稿操作、追加取得を開始しない。
- 開始待ち中のレスポンスは、投稿を含む一方で `access_allowed: false`、`feed_access_pending: true`、`remaining_seconds: 0`、`feed_access_expires_at: nil` を維持する。
- 開始待ち中に `page=2` 以降を指定しても最初のページを返し、追加ページへ進めない。
- 先読みで `feed_intro_seen_at`、`feed_access_pending`、`feed_access_expires_at` は変更しない。
- 先読み失敗はタスク完了の成功に影響させない。

### 3.3 初回説明未確認ユーザー

- 初回説明の確認状態は、ブラウザの `localStorage` ではなく、アカウントごとの `users.feed_intro_seen_at` で管理する。`NULL` は未確認、日時ありは確認済みを表す。
- フィードを開くと、先読み済みの実際の投稿をぼかした操作不能の背景として表示し、初回説明モーダルを表示する。
- 説明中はタイマー、投稿操作、スクロールによる追加取得、Action Cable購読を開始しない。
- 「OK」による `POST /api/feed/access` が成功した時点で、確認日時、開始待ちの解除、現在時刻から3分後の期限を整合性のある状態で確定する。
- 開始成功後は先読み済み投稿を再利用し、ぼかしと操作制限を解除する。
- 同じアカウントでは、別ブラウザ、再ログイン、ブラウザストレージ削除後もサーバー上の確認状態を引き継ぐ。別アカウントの確認状態とは混ざらない。

### 3.4 初回説明確認済みユーザー

- 「みんなを見る」などで実際にフィードを開いた時点で `POST /api/feed/access` を実行する。タスク完了からフィードを開くまでの時間は消費しない。
- 先読み済み投稿を即座に表示し、通常は「読み込んでいます…」を表示しない。
- 開始API成功前は投稿一覧を `inert` および `aria-hidden` にして、投稿操作、追加取得、Action Cable購読を開始しない。
- 開始API成功後に、サーバーが返した絶対期限を基準としてカウントダウンを開始し、投稿操作、追加取得、Action Cable購読を有効にする。
- 確認済みの `feed_intro_seen_at` は、閲覧開始時に上書きしない。

### 3.5 閲覧期限と期限外の制御

- 閲覧期限はサーバーの `feed_access_expires_at` を正とする。
- 開始APIの逐次・並行・重複実行では、最初に確定した期限を返し、期限を延長しない。
- 再読み込み、画面再訪、再ログイン後も同じサーバー期限を引き継ぐ。
- 期限切れ後の `GET /api/feed` は投稿を返さない。
- 期限切れ時は「3分経過しました」モーダルを表示し、投稿一覧と開いていたコメントパネルを操作できない状態にして、ホームへ戻れる。
- 閲覧開始前、期限がない状態、期限切れ後は、いいね追加・解除、コメント一覧取得・投稿をサーバー側で `403 Forbidden` として拒否する。

### 3.6 失敗と再試行

- 初回説明の「OK」が失敗した場合は、モーダルとぼかしを維持し、確認状態、閲覧期限、タイマー、投稿操作、Action Cable購読を開始しない。再試行成功時に状態を一度だけ確定する。
- 説明確認済みユーザーの開始APIが失敗した場合は、先読み投稿を保持したまま操作不能にし、再試行では開始APIだけを実行する。
- 先読みが失敗していた場合は、フィードを開いた際に開始APIを実行し、成功後に投稿を取得する。投稿取得中だけローディング表示を行う。
- 開始API成功後の投稿取得が失敗した場合は、開始APIを再実行せず、投稿GETだけを再試行し、最初に確定した期限を維持する。

## 4. テストデータと実施基準

| データ | 状態 | 用途 |
| --- | --- | --- |
| アカウントA | 初回説明未確認、完了可能なタスクあり | 初回説明、開始処理、失敗時の再試行 |
| アカウントB | 初回説明確認済み、完了可能なタスクあり | フィードを開いた時点での開始、先読み、再訪 |
| アカウントC | 閲覧期限切れ、完了可能な新しいタスクあり | 期限後制御、新しい権利の付与 |
| 投稿P | 他ユーザーの投稿、いいね・コメント可能 | 先読み、閲覧、操作の期限確認 |
| ブラウザContext 1・2 | Cookieとブラウザストレージを共有しない | 同一アカウントの確認状態引き継ぎ |

時間依存ケースでは実時間を3分待たず、Railsの `travel_to`、Playwright Clock、固定した絶対期限を使う。APIの閲覧期限を確認する自動テストでは、通信時間を伴う場合に約2秒の誤差を許容する。時刻を固定できるケースは固定時刻を基準に厳密に確認する。

## 6. 自動テストの種類と役割

| 種類 | 主な確認範囲 |
| --- | --- |
| フロントエンドAPI単体（Vitest） | フィード取得・開始APIの応答変換、開始待ち・期限切れ・認証失敗の扱い |
| Rails API・結合（RSpec） | 未使用権利の付与、先読みGETの非更新性、開始処理の整合性と排他性、期限計算、期限外API拒否、アカウント別の確認状態 |
| UI結合（APIモックPlaywright） | 先読み表示、モーダル、操作制限、カウントダウン、通信失敗と再試行、期限切れ画面、再読み込み・再訪・再ログイン |
| 実バックエンドE2E（Playwright） | 登録・タスク完了・初回説明確認と、独立したBrowserContextや再ログインをまたぐサーバー状態の引き継ぎ |

実時間を待つテストは避ける。正確な期限計算、状態更新、並行実行はRSpecへ寄せ、Playwrightはユーザーが見る状態遷移とレイヤー間の接続を確認する。

## 8. まだ不足している確認

- FA-03はRSpecと状態付きモックのPlaywrightで各操作を確認しているが、再読み込み、再訪、再ログインを同じ実バックエンド上でまとめて行う専用E2Eはない。現在の仕様を否定する不足ではないため、保守コストとのバランスを見て追加を判断する。
- ブラウザが長時間バックグラウンドにある場合や端末時計が大きくずれた場合に、表示中の残り時間を再同期する専用テストはない。APIと再取得時の期限はサーバーを正としている。
- Action Cableは開始前にフロントエンドで購読せず、期限切れ時に画面操作を止めているが、サーバー側で接続時・配信時に閲覧期限を検査する専用制御とテストはない。
- 複数端末から同時に同じ閲覧権利を利用した場合の専用UIや競合シナリオは未定義である。サーバー上の絶対期限は共通となる。
- コメント削除機能は現行に存在しないため、期限外のコメント削除テストは対象外である。

## 9. 仕様判断の結果

1. 未使用閲覧権利は蓄積せず、1回分だけ保持する。新しいタスク完了時は、新しい1回分の未使用権利へ置き換える。
2. 初回説明の確認状態にかかわらず、タスク完了時には期限を開始せず、実際にフィードを開いた時点から3分間を開始する。
3. 開始待ち中の `GET /api/feed` は、背景表示・先読み用の最初のページを返すが、閲覧権利や期限を変更しない。追加ページは返さない。
4. 初回説明の確認状態はアカウントごとにサーバーへ保存し、確認状態の保存と閲覧開始を同じ処理で整合性を保って確定する。
5. 一度確定した閲覧期限は、重複操作、再読み込み、再訪、再ログイン、開始APIの逐次・並行実行では延長しない。
6. 閲覧開始前と期限切れ後は、いいね追加・解除、コメント一覧取得・投稿をサーバー側で拒否する。
7. 開始API成功後の投稿取得失敗では、開始APIを再実行せず、同じ絶対期限を使って投稿取得だけを再試行する。
